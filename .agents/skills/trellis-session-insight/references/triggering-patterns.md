# 触发模式

以下用户表达应让 AI 想到 `trellis mem`。可用它们校准判断：用户消息命中这些模式却未使用 `mem`，很可能漏掉了明显的历史检索需求。

模式按表达背后的*意图*分组，不按表面措辞。同一意图可以出现在不同语言和语体中。

## 回忆过去的解法

用户在问“我们（或我）以前如何解决”。历史对话保存答案；代码库只展示结果，未必说明推理过程。

- “上次我们怎么解决的？”
- “关于 X 最后是怎么处理的？”
- “我们不是已经处理过一次了吗？”
- “上次怎么解的？”
- “之前是怎么搞定 X 的？”
- “我记得以前修过类似的。”

调用：`trellis mem search "<symptom keyword>" --global --limit 10`，再对最接近的命中使用 `context`。

## 检索决策

用户提到的决策保存在旧对话中，未写入已提交文件。查看需求讨论窗口。

- “关于 X 当时怎么决定的？”
- “我们决定用 Postgres 还是 SQLite？”
- “选 X 而不是 Y 的原因是什么？”
- “我们当时为啥选了 X 而不是 Y？”
- “关于 X 我们之前是怎么定的？”
- “之前讨论过 X 的方案吗？”

调用：`trellis mem search "<decision keyword>"` 找到会话，再用 `extract <id> --phase brainstorm` 恢复讨论。

## 跨会话继续

用户隔了一段时间恢复工作，上下文没有明说。

- “我们做到哪了？”
- “从上次继续。”
- “从之前停下的地方接着做。”
- “继续上次的。”
- “我们上次做到哪了？”
- “接着昨天那个任务。”

调用：先用 `trellis mem list --cwd <project-path>` 列出当前项目近期会话，或用 `trellis mem search "<task-slug>" --cwd <project-path>` 按任务标识搜索；核对命中对话后再对相关会话使用 `extract`。本机 0.6.17 不提供 `--task` 过滤，不能把项目会话列表当作已经匹配当前任务。

## 排查熟悉的错误

当前错误像是以前见过的问题。历史会话可能包含解决路径。

- “我感觉之前遇到过这个。”
- “这不是像上个月那个错误吗？”
- “和 X 里遇到的超时一样。”
- “这个错好像之前见过。”
- “这个 bug 是不是上次那个？”
- “怎么又是这个 error？”

调用：`trellis mem search "<error message fragment>" --global`。使用真实错误信息中简短且有辨识度的片段定位。

## 发现自己的重复模式

用户想知道是否一直重复同一类错误或决策。

- “我是不是总犯这个错误？”
- “我遇到 X 多少次了？”
- “这是不是反复出现的问题？”
- “我每次都踩这个坑吗？”
- “我老犯这个错？”
- “这类问题之前出现过几次？”

调用：`trellis mem search "<topic>" --global --limit 50`，查看列表中的日期和项目。必要时选两三个会话 `extract` 比较。

## 收尾复盘（按需）

用户明确要求回顾本任务时才执行，不作为强制步骤。

- “总结一下这个任务做了什么。”
- “有哪些关键决策和意外？”
- “写一下这一轮的经验教训。”
- “总结一下这次的经验。”
- “记一下这次踩的坑。”
- “复盘下这个任务。”

调用：从 `.trellis/.runtime/sessions/*.json` 核对当前任务的会话 ID，或用 `trellis mem search "<task-slug>" --cwd <project-path>` 搜索并核对相关对话，再分别 `extract <id> --phase brainstorm` 与 `--phase implement`。展示总结，尽可能给出具体的文件:行号引用。是否将总结写入 PRD、规范或笔记由用户决定；可以建议，不自动写入。

## 反模式：这些情况不要使用 `mem`

- “这个函数做什么？” → 读文件。
- “这个测试为什么失败？” → 读测试输出和文件。
- “我们代码库里 X 应该采用什么模式？” → 搜索 / 读取规范。
- “Y 最新的 npm 版本是什么？” → 调用 `npm view`。
- “修复这个错误。” → 排查。只有怀疑存在相关历史上下文时才用 `mem`，否则只会增加噪声。

判断标准不变：有经验的同事会不会在回答前先问“我们是不是已经讨论过”？会，就使用 `mem`；不会，就不用。
