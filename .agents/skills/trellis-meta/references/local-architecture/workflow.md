# 本地工作流系统

`.trellis/workflow.md` 是用户项目内部 Trellis 工作流的权威源。AI 无需 Trellis 源码也能理解当前项目如何推进任务；读取此文件即可。

## 文件职责

`.trellis/workflow.md` 有三个职责：

1. **说明工作流阶段**：规划、执行、收尾。
2. **定义技能路由**：用户表达某种意图时，AI 应使用哪个技能或代理。
3. **提供工作流状态提示块**：钩子可将当前状态对应的提示块注入对话。

## 当前阶段模型

```text
阶段 1：规划 → 澄清要构建什么，产出 prd.md 与必要研究
阶段 2：执行 → 按 PRD 和规范实施，然后检查
阶段 3：收尾 → 最终验证、保存经验并完成收尾
```

每个阶段包含编号步骤，例如 `1.3 配置上下文`。这些数字不是 `task.json` 中的运行字段，而是供 AI 与人类阅读的工作流结构。

## 技能路由

`workflow.md` 按平台能力区分路由：

- 支持子代理的平台：实施默认派发 `trellis-implement`，检查默认派发 `trellis-check`。
- 不支持子代理的平台：主会话读取 `trellis-before-dev` 等技能，然后直接执行。

修改本地 AI 行为时，应先更新 `workflow.md` 中的路由说明，再检查对应平台的技能、命令或代理文件是否也需同步。

## 工作流状态提示块

`workflow.md` 的阶段索引中包含以下状态块：

```text
[workflow-state:no_task]
...
[/workflow-state:no_task]
```

钩子根据当前任务状态选择正确块并注入对话。常见状态包括：

| 状态 | 含义 |
| --- | --- |
| `no_task` | 当前会话没有活动任务。 |
| `planning` | 任务仍处于需求、研究或上下文配置阶段。 |
| `in_progress` | 任务已进入实施与检查。 |
| `completed` | 已完成状态的保留提示；当前归档命令同时写入此状态、移动任务并清除指针，正常流程不会停留在该提示。 |

用户希望改变“无任务时是否创建任务”“何时可以跳过创建任务”或“是否必须使用子代理”等策略时，应编辑这些状态块及其上方路由表。

## 本地修改模式

常见变更：

| 目标 | 修改位置 |
| --- | --- |
| 添加阶段 | 更新阶段索引、阶段正文、路由和状态块。 |
| 修改任务创建策略 | 更新 `no_task` 状态块和阶段 1 说明。 |
| 修改默认实施/检查路径 | 更新阶段 2 与技能路由。 |
| 修改收尾流程 | 更新阶段 3 与 `finish-work` 相关说明。保留职责分工：阶段 3.4 由主会话在检查通过后按授权自主分批提交本任务改动；阶段 3.5 执行 `/finish-work`（归档 + 记录会话）。遵循本地工作流的工作区检查门槛，先处理未提交的本任务改动，再归档。 |
| 修改平台差异 | 更新按平台分组的路由说明。 |

编辑后，让 AI 重新读取 `.trellis/workflow.md`；不要假设旧对话中的流程仍然有效。

## 与平台文件的关系

`workflow.md` 是本地工作流的语义中心，但各平台还可以有各自入口文件：

- 技能，例如 `trellis-brainstorm` 和 `trellis-check`。
- 命令/提示/工作流，例如 continue 和 finish-work。
- 钩子，例如 session-start 或工作流状态注入。

如果只修改 `workflow.md`，平台入口文件可能仍保留旧表述。用户希望改变“AI 实际做什么”时，也应检查相关平台目录。
