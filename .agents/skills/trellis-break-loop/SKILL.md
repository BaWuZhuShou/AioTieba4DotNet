# 打破循环：深入缺陷分析

调试完成后，用本技能深入分析，避免“修复缺陷 → 遗忘 → 再次发生”的循环。

---

## 分析框架

从以下五个维度分析刚刚修复的缺陷：

### 1. 根因类别

此缺陷属于哪一类？

| 类别 | 特征 | 示例 |
|----------|-----------------|---------|
| **A. 缺少规范** | 没有说明应如何处理 | 新功能没有检查清单 |
| **B. 跨层契约** | 层间接口不清楚 | API 返回格式与预期不同 |
| **C. 变更传播遗漏** | 改了一处，漏了其他位置 | 修改函数签名却漏改调用处 |
| **D. 测试覆盖缺口** | 单元测试通过，集成失败 | 单独可用，组合后出错 |
| **E. 隐含假设** | 代码依赖未记录的假设 | 时间戳单位为秒还是毫秒 |

### 2. 修复为何失败（若适用）

若成功前尝试过多次修复，逐次分析：

- **只修表象**：解决症状，未解决根因
- **范围不全**：找到了根因，但未覆盖全部情况
- **工具限制**：搜索遗漏、类型检查不够严格
- **思维局限**：一直查看同一层，没有考虑跨层关系

### 3. 预防机制

哪些机制能防止问题再次发生？

| 类型 | 说明 | 示例 |
|------|-------------|---------|
| **文档** | 写下来供后续人员了解 | 更新思考指南 |
| **架构** | 从结构上排除错误 | 类型安全的封装 |
| **编译期** | 严格类型检查，不留绕过入口 | 签名变化触发编译错误 |
| **运行时** | 监控、告警和扫描 | 检测孤立实体 |
| **测试覆盖** | 端到端和集成测试 | 验证完整流程 |
| **代码评审** | 检查清单和 PR 模板 | 提醒检查关键事项 |

### 4. 系统性扩展

该缺陷揭示了哪些更广泛的问题？

- **相似问题**：其他哪些地方可能存在同样的问题？
- **设计缺陷**：是否存在基础架构问题？
- **流程缺陷**：开发流程能否改进？
- **知识缺口**：团队是否缺少某方面的理解？

### 5. 知识沉淀

将发现固化到系统中：

- [ ] 更新 `.trellis/spec/guides/` 思考指南
- [ ] 更新相关 `.trellis/spec/` 文档
- [ ] 创建问题记录（若适用）
- [ ] 为根本修复创建功能事项
- [ ] 必要时更新检查指南

## 核心理念

> **调试除了修复当前缺陷，还应建立防止同类缺陷再次发生的机制。**

三个层次的收获：
1. **战术**：如何修复这一个缺陷
2. **策略**：如何预防这一类缺陷
3. **思维**：如何拓展分析方式

花 30 分钟分析，可能省去以后 30 小时的调试。

## 思考框架：贝叶斯推理

多个根因都合理且证据不足时，依据新证据调整判断，不固守初始假设。

### 步骤 1：建立先验

调查前，说明当前判断和依据：

| 假设 | 先验概率 | 依据 |
|------------|-------|-----------|
| H1：[原因 A] | 40% | 此类问题最常见的原因 |
| H2：[原因 B] | 30% | 当前环境下合理 |
| H3：[其他] | 30% | 其余可能性 |

先验概率之和必须为 100%。无法合理分配时先调查。

### 步骤 2：观察证据

记录发现，并具体说明可靠性：

- 实际观察到了什么？
- 可靠性如何？（测试输出 > 日志消息 > 用户报告 > 直觉）
- 是否有多个假设都能解释它？

### 步骤 3：更新判断

对每个假设询问：**若该假设成立，出现这份证据的可能性有多大？**

调整方向比精确计算更重要：
- H1 强烈预测该证据 → 提高 H1 概率
- 证据与 H2 矛盾 → 降低 H2 概率
- 各假设下出现概率相同 → 不更新

### 步骤 4：寻找有区分力的证据

不要重复收集同类证据，应寻找在主要假设之间**明显不同**的证据。

> H1 与 H3 接近时，思考：“什么现象在 H1 成立时会出现，而 H3 成立时不会？”然后验证。

### 步骤 5：说明置信度

| 置信度 | 行动 |
|------------|--------|
| 90% 以上 | 实施修复并监测 |
| 70–90% | 推进，同时增加补充检查 |
| 50–70% | 作出修复决定前验证假设 |
| 低于 50% | 继续收集证据，不猜测 |

证据不完整时，不表达非黑即白的确定性。使用“最可能”“合理但可能性较低”“值得调查”等措辞。

### 常见谬误

| 谬误 | 示例 | 纠正方式 |
|---------|---------|------------|
| **忽视基础发生率** | 测试失败就断定代码坏了 | 测试因其他原因失败的频率是多少？ |
| **确认偏误** | 先认定是竞态，再只找竞态证据 | 主动寻找反驳首选假设的证据 |
| **锚定效应** | 上次是缓存，这次大概也是 | 基于当前上下文建立先验，不沿用昨日缺陷 |

## 分析后的立即行动

完成分析后，**必须立即**：

1. **更新规范或指南** — 不只列待办，要实际修改相关文件：
   - 跨平台问题 → 更新已有的 `cross-platform-thinking-guide.md`；本仓库无此文件时，写入实际负责该契约的规范，不引用不存在的路径
   - 跨层问题 → 更新 `cross-layer-thinking-guide.md`
   - 代码复用问题 → 更新 `code-reuse-thinking-guide.md`
   - 领域问题 → 更新 `backend/*.md` 或 `frontend/*.md`

2. **同步模板** — 修改 `.trellis/spec/` 后，仅当当前仓库实际包含 `src/templates/markdown/spec/` 上游模板树时同步；不要在业务项目中创建虚构模板目录。

3. **纳入工作提交** — 规范更新是主要产物，不只是分析文字。交由主会话按工作流阶段 3.4 检查后统一自动提交；子代理不得自行提交。

> **分析必须落到更新后的规范，不能只停留在聊天里。**
