# Trellis 需求探索

## 不可跳过的规划契约

用户提出构建、实施、修复、重构或“继续做”，不代表可以跳过规划。创建任务授权也不等于实施授权。

每个非简单任务在实施前，用户都必须在初始请求后至少回复一次。若无需澄清，该回复必须批准下文所述的最终规划摘要。

只要仍有由用户决定的产品、范围、体验、兼容性、风险或验收问题尚未解决，就以一个最有价值的问题结束本轮。不要修改产品代码、派发实施或运行 `task.py start`。

## 不可跳过的证据规则

能够通过探索代码库回答的问题，先探索代码库，不向用户提问。

这是强制要求。提问前，先检查代码、测试、配置、文档、已有规范或任务历史中是否已有答案。

不要请用户确认仓库能够回答的事实。只询问产品意图、偏好、范围、风险容忍度、验收行为，或检查后仍有歧义的决策。

仓库证据用于确定当前行为和技术约束。用户期望的行为、功能范围边界和体验偏好不能仅由仓库证据决定，即使已有模式也一样；已有模式可以作为选项和建议依据，不能代替用户决策。

---

在阶段 1 规划期间使用本技能，将用户请求转化为明确的需求和规划文档。

## 前置条件

只有已获得创建任务授权，且用户准备进入 Trellis 规划时，才使用本技能。

若尚无任务，创建一个：

```bash
TASK_DIR=$(python3 ./.trellis/scripts/task.py create "<简短任务标题>" --description "<一句话摘要>" --slug <slug>)
```

标题从用户请求中提取，保持简洁。标题和 `--description` 都必须非空：`create` 拒绝空值，归档也会拒绝任一字段为空的记录。slug 不含日期前缀；`task.py create` 自动添加 `MM-DD-`。中文标题应显式提供稳定的英文 slug。

`task.py create` 会创建默认 `prd.md`。提出后续问题前，先将当前理解写入该文件。

## 规划流程

1. 在 `prd.md` 记录用户请求和最初已知事实。
2. 提问前检查可用证据：
   - 代码、测试、测试夹具和配置
   - README、文档、现有规范和领域说明
   - 相关 Trellis 任务、研究文件和已有会话历史
3. 将发现分为：
   - 已确认事实
   - 仍需用户决定的产品意图
   - 仍需用户决定的范围或风险
   - 可能不在范围内的事项
4. 仍有用户决策未定时，提出最有价值的一个问题，说明建议和取舍，然后停止。本轮不要同时开展实施。
5. 每次用户回答后更新 `prd.md`，重新梳理待决事项，从步骤 2 继续。
6. 没有用户决策遗留时，为复杂任务创建或更新 `design.md` 和 `implement.md`。
7. 执行需求收敛检查，再执行 PRD 收敛整理。
8. 展示最终规划摘要并停止。同一轮不要运行 `task.py start` 或修改产品代码。
9. 只有用户在后续消息中明确批准最新规划摘要，才授权执行 `task.py start` 和实施。批准后文档发生实质变化时，重新进行最终评审。

不要自行创造项目专属的产品或规范层级。仓库已有产品、领域或规范文档时沿用；没有时依据现有证据推进。

## 提问规则

每条消息只问一个问题。

每个问题必须包含：

- 需要作出的决策
- 答案为什么重要
- 你的建议
- 选择其他方案的取舍

不要询问是否搜索、检查文件或继续探索等过程问题。直接完成证据工作。只有剩余问题属于产品决策、偏好、范围边界或风险容忍度时，才向用户提问。

建议不是默认选项。不能仅因用户要求实施，就替用户选定你推荐的产品决策。

请求和仓库证据已经解决全部决策时，不制造澄清问题；直接进入最终规划摘要，之后仍需用户明确批准。

最终评审是必要的阶段转换门槛，不属于禁止的过程问题。创建任务授权、最初的实施请求，以及最新最终摘要展示之前的批准，都不能满足这个门槛。

## 思考框架：第一性原理分析

需求模糊、方案过度设计，或即将因为“大家都这样做”而增加复杂度时，先拆解基本事实，再据此推导。

### 步骤 1：重述问题

去掉实现细节，用一句话表达。

> 不合适：“需要给用户资料接口加 Redis 缓存。”
> 合适：“用户资料加载太慢。”

### 步骤 2：列出基本事实

什么是确定成立的事实，而不是观点或惯例？

| 类别 | 示例 |
|----------|----------|
| **物理约束** | 网络延迟 ≥ 0，磁盘 I/O 有上限 |
| **业务规则** | 用户必须看到自己的数据 |
| **技术不变量** | 数据必须一致 |
| **用户需求** | 用户希望在 Y 秒内获得 X |

### 步骤 3：质疑假设

针对当前计划的每个组成部分：

- **是事实还是惯例？** “一直用 REST”——为什么？
- **去掉它会怎样？** 没有任何功能受影响，就可能不需要。
- **解决实际问题还是表象？** 追溯因果链。
- **谁从这份复杂度获益？** 若无人获益，简化。

### 步骤 4：从事实构建方案

1. 从满足全部基本事实的最小可行机制开始
2. 只有具体事实要求时才增加复杂度
3. 每次增加都要回答：“哪条事实要求这样做？”

### 步骤 5：验证

- 方案是否解决最初的问题？
- 哪些假设需要验证？
- 最简单的验证实验是什么？

## 需求收敛门槛

最终评审前，逐项确认：

- 用户结果和产品价值明确
- 范围内及范围外行为明确
- 验收标准描述可观察结果
- 用户负责的产品、范围、体验、兼容性和风险决策已解决
- 没有阻塞性的待解决问题
- 技术未知项已研究，或在不改变最小可用行为的前提下明确延期

轻量任务可以省略 `design.md` 和 `implement.md`，但不能跳过证据检查、需求收敛、最终评审和新的实施批准。

最终规划摘要必须包含目标、范围内内容、范围外内容、验收标准、关键决策、相关风险或延期事项，以及文档状态。

## 文档规则

`prd.md` 记录需求和验收：

- 目标和用户价值
- 已确认事实
- 需求
- 验收标准
- 范围外内容
- 仍阻塞规划的问题

`design.md` 记录复杂任务的技术设计：

- 架构和边界
- 数据流和契约
- 兼容性与迁移说明
- 重要取舍
- 运维或回滚考虑

`implement.md` 记录复杂任务的执行计划：

- 有序实施清单
- 验证命令
- 高风险文件或回滚点
- `task.py start` 前的后续检查

轻量任务可以只有 `prd.md`。复杂任务在 `task.py start` 前必须具备 `prd.md`、`design.md` 和 `implement.md`。

`implement.md` 不能替代 `implement.jsonl`。派发子代理的工作流要求 `implement.jsonl` 和 `check.jsonl` 在 `task.py start` 前各有至少一条真实规范或研究条目；空清单或仅含旧 `_example` 占位行均不算就绪。内联工作流跳过该 JSONL 门槛，因为阶段 2 通过 `trellis-before-dev` 加载上下文。

## PRD 收敛整理

宣布规划就绪或执行 `task.py start` 前，按上述文档规则的最终结构重整一次 `prd.md`。这不是可选清理，而是最后一道规划门槛。

整理必须无损：

- 将重复事实合并至一个权威章节。
- 把“已知内容”“假设”和已解决的“待解决问题”等临时探索章节，归并到目标、背景、需求、技术备注或验收标准。
- 删除已解决的问题，不留下空白或已经回答的章节。
- 缺陷列表与需求列表描述同一工作时合并；保留每项缺陷的严重性、证据及 `file:line` 定位，并归属到对应需求。
- 保留所有 `file:line` 定位、决策、约束、需求 ID 和验收映射。
- 仍有阻塞问题时，不进入最终评审。

整理后从头到尾阅读 `prd.md`，确认不存在无新增信息的跨章节重复事实。

## 质量门槛

宣布规划就绪前：

- `prd.md` 有可测试的验收标准。
- `prd.md` 已完成收敛整理：没有未处理的临时探索章节、跨章节重复事实，也没有丢失定位、决策或验收映射。
- 仓库能够回答的问题已通过检查解决。
- 没有阻塞性的待解决问题。
- 复杂任务已有 `design.md` 和 `implement.md`。
- 子代理任务的 `implement.jsonl` 和 `check.jsonl` 都有真实条目；只有示例的清单不算就绪。
- 已向用户展示最新最终规划摘要。
- 用户在后续消息中明确批准该摘要并同意实施。

不要仅因用户最初要求实施，就直接开始实施。
