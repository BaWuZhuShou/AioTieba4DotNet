# 规范编写

Trellis 规范是供后续代理使用的编码指南，应说明如何在当前仓库工作，而非泛泛介绍项目可以如何组织。

## 依据证据编写

每项重要规则应至少有一种依据：

- 展示推荐模式的源码文件。
- 展示预期行为的测试文件。
- 定义约定的项目文档。
- 在多个文件中反复出现的模式。

只有能使规则更清楚时才使用短代码片段。优先链接文件路径，并指出符号或行为。

## 文件结构

规范目录树应与项目一致：

- 保留 `index.md` 作为规范目录的导航文件。
- 开发者会独立查找的主题应拆分。
- 分开会重复同一规则的主题应合并。
- 删除不适用的模板文件。
- 为模板遗漏的重要本地模式新增文件。

## 内容标准

好的规范章节应包含：

- 规则适用的情形。
- 应遵循的本地模式。
- 证明该模式的源码或测试文件。
- 常见错误或反模式。
- 具体且可靠的验证命令或检查项。

避免：

- 占位文字。
- 泛泛的框架建议。
- 只适用于某个代理宿主的工具指令。
- 大段复制的代码。
- 基于单个偶然实现细节制定规则。

## 示例结构

```markdown
## 命令处理器

命令处理器应分开处理参数解析、校验与副作用。本地模式是：

- 在命令边界解析 CLI 参数。
- 调用核心逻辑前，将原始输入转换为有类型的任务选项。
- 文件系统写入放在命令或服务层，不放在模板辅助函数中。

参考文件：
- `packages/cli/src/commands/example.ts`
- `packages/cli/test/commands/example.test.ts`

避免将原始 `process.argv` 或未经校验的配置对象传入共享辅助函数。
```

## 最终检查

完成前运行：

```bash
grep -R "To be filled\\|TODO: fill\\|placeholder" .trellis/spec
```

同时检查链接、索引文件，以及是否还有规范描述的是模板而非当前仓库。
