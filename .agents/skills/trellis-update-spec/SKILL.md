# 更新代码规范：记录可执行契约

调试、实施或讨论中获得有价值的知识时，用本技能更新相关代码规范。

**时机**：完成任务、修复缺陷或发现新模式之后。

---

## 代码规范优先原则（关键）

本项目实施工作中的“规范”指**代码规范**：
- 可执行契约，不只是原则性说明
- 具体签名、载荷字段、环境变量键和边界行为
- 可测试的校验及错误行为

涉及基础设施或跨层契约时，必须达到代码规范的具体程度。

### 必须触发的情况

变更包含以下任一内容时，必须写到代码规范层面：
- 新增或修改命令、API 签名
- 跨层请求或响应契约变化
- 数据库 schema 或迁移变化
- 基础设施集成（存储、队列、缓存、密钥、环境配置接线）

### 必需产物：七个章节

触发上述条件的任务必须包含：
1. 范围与触发条件
2. 签名（命令、API、数据库）
3. 契约（请求、响应、环境）
4. 校验与错误矩阵
5. 良好、基准与错误场景
6. 必需测试及断言点
7. 错误与正确示例（至少一组）

---

## 何时更新代码规范

| 触发条件 | 示例 | 目标规范 |
|---------|---------|-------------|
| **实现功能** | 新增集成或模块 | 相关规范文件 |
| **作出设计决策** | 在简单性与可扩展性之间作出选择 | 相关规范的“设计决策”章节 |
| **修复缺陷** | 发现错误处理中的隐蔽问题 | 相关规范，如错误处理文档 |
| **发现模式** | 发现更合适的代码组织方式 | 相关规范文件 |
| **遇到陷阱** | 发现必须先做 X 再做 Y | 相关规范的“常见错误”章节 |
| **形成约定** | 团队同意某种命名模式 | 质量指南 |
| **新增思考触发点** | 做 Y 前不要忘记检查 X | `guides/*.md` 的检查项 |

**关键认识**：代码规范不只记录问题。每次功能实施都有设计决策和契约，未来 AI 和开发者需要依据它们安全实施。

## 规范结构概览

```
.trellis/spec/
├── <layer>/           # 各层编码标准，例如 backend/、frontend/、api/
│   ├── index.md       # 概览和链接
│   └── *.md           # 具体主题指南
└── guides/            # 思考清单，不是编码规范
    ├── index.md       # 指南索引
    └── *.md           # 具体主题思考指南
```

### 关键区别：代码规范与思考指南

| 类型 | 位置 | 用途 | 内容风格 |
|------|----------|---------|---------------|
| **代码规范** | `<layer>/*.md` | 告诉 AI 如何安全实施 | 签名、契约、矩阵、场景和测试点 |
| **思考指南** | `guides/*.md` | 帮助 AI 知道该考虑什么 | 检查清单、问题和规范引用 |

**判断规则**：

- 内容说明**如何写代码** → 放入对应规范层目录
- 内容说明**编写前考虑什么** → 放入 `guides/`

**示例**：

| 收获 | 错误位置 | 正确位置 |
|----------|----------------|------------------|
| 此任务应使用 API X 而非 API Y | ❌ `guides/`，对思考指南过于具体 | ✅ 相关规范文件，记录具体约定 |
| 做 Y 时记得检查 X | ❌ 规范文件，过于抽象 | ✅ `guides/`，作为思考清单 |

**思考指南应是简短清单，并指向规范**，不要复制详细规则。

## 更新流程

### 步骤 1：确认学到了什么

回答：

1. **学到了什么？** 具体说明。
2. **为什么重要？** 它能防止什么问题？
3. **应放在哪里？** 哪份规范负责？

### 步骤 2：分类更新

| 类型 | 说明 | 操作 |
|------|-------------|--------|
| **设计决策** | 为什么选择方案 X 而不是 Y | 加入“设计决策”章节 |
| **项目约定** | 本项目如何处理 X | 在相关章节加入示例 |
| **新模式** | 新发现的可复用方法 | 加入“模式”章节 |
| **禁止模式** | 会导致问题的做法 | 加入“反模式”或“禁止事项”章节 |
| **常见错误** | 容易发生的错误 | 加入“常见错误”章节 |
| **约定** | 已达成一致的标准 | 加入相关章节 |
| **陷阱** | 不明显的行为 | 添加提示说明 |

### 步骤 3：阅读目标代码规范

编辑前阅读当前规范：
- 理解现有结构
- 避免重复内容
- 找到适合更新的章节

```bash
cat .trellis/spec/<category>/<file>.md
```

### 步骤 4：更新文档

遵循：

1. **具体**：给出具体示例，不只讲抽象规则
2. **解释原因**：说明能防止什么问题
3. **展示契约**：加入签名、载荷字段和错误行为
4. **展示代码**：关键模式提供代码片段
5. **保持简短**：每个章节聚焦一个概念

### 步骤 5：必要时更新索引

新增章节或规范状态变化时，更新该类别的 `index.md`。

## 更新模板

### 基础设施或跨层工作的必需模板

```markdown
## 场景：<名称>

### 1. 范围与触发条件
- 触发条件：<为何必须写到代码规范层面>

### 2. 签名
- 后端命令、API 或数据库签名

### 3. 契约
- 请求字段（名称、类型、约束）
- 响应字段（名称、类型、约束）
- 环境变量键（必填或可选）

### 4. 校验与错误矩阵
- <条件> -> <错误>

### 5. 良好、基准与错误场景
- 良好：...
- 基准：...
- 错误：...

### 6. 必需测试
- 单元、集成或端到端测试及其断言点

### 7. 错误与正确示例
#### 错误
...
#### 正确
...
```

### 添加设计决策

```markdown
### 设计决策：[决策名称]

**背景**：要解决什么问题？

**考虑过的选项**：
1. 方案 A — 简述
2. 方案 B — 简述

**决策**：选择方案 X，因为……

**示例**：
\`\`\`typescript
// 具体实施方式
<代码示例>
\`\`\`

**扩展方式**：未来如何扩展……
```

### 添加项目约定

```markdown
### 约定：[约定名称]

**内容**：简要描述约定。

**原因**：本项目为什么这样做。

**示例**：
\`\`\`typescript
// 如何遵循该约定
<代码示例>
\`\`\`

**相关内容**：相关约定或规范链接。
```

### 添加新模式

```markdown
### 模式名称

**问题**：该模式解决什么问题？

**方案**：简述处理方式。

**示例**：
\`\`\`
// 合适的写法
<代码示例>

// 不合适的写法
<代码示例>
\`\`\`

**原因**：解释为什么更合适。
```

### 添加禁止模式

```markdown
### 禁止事项：模式名称

**问题**：
\`\`\`
// 不要这样做
<错误代码示例>
\`\`\`

**不合适的原因**：解释问题。

**替代方式**：
\`\`\`
// 应这样做
<正确代码示例>
\`\`\`
```

### 添加常见错误

```markdown
### 常见错误：简述

**现象**：哪里出了问题

**原因**：为什么发生

**修复**：如何纠正

**预防**：以后如何避免
```

### 添加陷阱提示

```markdown
> **注意**：简述不明显的行为。
>
> 说明发生条件和处理方式。
```

## 交互模式

不确定该更新什么时，回答以下提示：

1. **刚完成了什么？**
   - [ ] 修复缺陷
   - [ ] 实现功能
   - [ ] 重构代码
   - [ ] 讨论方案

2. **学到或决定了什么？**
   - 设计决策：为什么选择 X 而非 Y
   - 项目约定：本项目如何处理 X
   - 不明显的行为：陷阱
   - 更合适的方法：模式

3. **未来的 AI 或开发者需要知道吗？**
   - 需要理解代码如何工作 → 更新规范
   - 需要维护或扩展功能 → 更新规范
   - 需要避免重复犯错 → 更新规范
   - 只是一次性实现细节 → 可以考虑跳过

4. **属于哪个领域？**
   - [ ] 后端代码
   - [ ] 前端代码
   - [ ] 跨层数据流
   - [ ] 代码组织或复用
   - [ ] 质量或测试

## 质量检查清单

结束代码规范更新前：

- [ ] 内容是否具体且可执行？
- [ ] 是否包含代码示例？
- [ ] 是否解释了原因，而不只描述做法？
- [ ] 是否包含可执行签名或契约？
- [ ] 是否包含校验与错误矩阵？
- [ ] 是否包含良好、基准和错误场景？
- [ ] 是否包含必需测试及断言点？
- [ ] 是否放在正确的代码规范文件？
- [ ] 是否与现有内容重复？
- [ ] 新成员是否能理解？

## 与其他命令的关系

```
开发流程：
  获得新知识 → update-spec（Trellis 命令）→ 知识已记录
       ↑                                  ↓
  break-loop（Trellis 命令）←──────────── 后续会话受益
  （深入缺陷分析）
```

- `break-loop`（Trellis 命令）— 深入分析缺陷，常会发现需要更新的规范
- `update-spec`（Trellis 命令）— 实际执行规范更新
- `finish-work`（Trellis 命令）— 提醒检查规范是否需要更新

---

## 核心理念

> **代码规范持续演进。每次调试和新发现，都是让实施契约更清楚的机会。**

目标是形成**团队共享记忆**：
- 一个人学到的知识让所有人受益
- AI 在一个会话学到的内容能保留到后续会话
- 将错误转化为有文档依据的防护规则
