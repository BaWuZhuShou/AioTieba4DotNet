# 代码质量检查

全面验证最近编写的代码，涵盖规范符合性、跨层安全和提交前检查。

---

## 步骤 1：确认变更内容

```bash
git diff --name-only HEAD
git status
```

## 步骤 2：阅读任务文档和适用规范

按顺序读取当前任务文档：

- `prd.md`
- `design.md`（若存在）
- `implement.md`（若存在）

```bash
python3 ./.trellis/scripts/get_context.py --mode packages
```

对每个受影响的包或层，读取规范索引并遵循其**质量检查**章节：

```bash
cat .trellis/spec/<package>/<layer>/index.md
```

读取索引引用的具体指南。索引只是入口，不能代替指南正文。

## 步骤 3：运行项目检查

运行与变更相关的项目 lint、类型检查和测试命令。修复失败后再继续。

## 步骤 4：对照清单评审

### 代码质量

- [ ] Lint 是否通过？
- [ ] 类型检查是否通过（若适用）？
- [ ] 测试是否通过？
- [ ] 是否清理了调试日志？
- [ ] 是否没有压制警告或绕过类型安全？

### 测试覆盖

- [ ] 新增函数是否需要并具备有意义的单元测试？
- [ ] 缺陷修复是否需要并具备回归测试？
- [ ] 行为变化是否同步更新相关测试？

### 规范同步

- [ ] 是否需要更新 `.trellis/spec/`，记录新模式、约定或经验？

> 思考：本轮修复的缺陷或发现的隐含知识，是否值得记录，避免未来再遇到？若是，更新相关规范。

### 范围纪律

- [ ] 是否整理了任务并未要求的代码？
- [ ] 是否为尚不存在的场景增加抽象、配置或扩展点？
- [ ] 是否为不可能出现的状态增加推测性兜底？
- [ ] 是否修改了验收范围未涉及的文件？
- [ ] 是否只在调用方增加绕行方案，而没有在行为实际所属位置修复？

## 步骤 5：跨层检查维度（若适用）

变更仅涉及一层时跳过。

### A. 数据流（涉及至少三层）

- [ ] 读取流程是否正确：存储 → 服务 → API → 界面？
- [ ] 写入流程是否正确：界面 → API → 服务 → 存储？
- [ ] 类型和 schema 是否在层间正确传递？
- [ ] 错误是否正确传播到调用方？

### B. 代码复用（修改常量、创建工具函数）

- [ ] 创建前是否搜索了已有相似代码？
  ```bash
  rg "pattern" src/
  ```
- [ ] 相同值重复时，是否表示调用方必须一起变化的稳定概念？只有此时才抽取；当前恰好相同的两个字面量应保持独立。
- [ ] 批量修改后，是否更新了所有相关位置？

### C. 导入与依赖（新建文件）

- [ ] 导入路径是否正确（相对与绝对路径）？
- [ ] 是否没有循环依赖？

### D. 同层一致性

- [ ] 同层其他使用相同概念的位置是否一致？

---

## 步骤 6：报告并修复

报告发现的每项违规，然后按以下规则处理：

- 机械性局部问题（lint 小问题、缺失类型、错误导入、无效分支、失败断言）→ 原地修复，再运行项目检查。
- 设计或判断问题（共享概念命名、移动模块边界、改变公共接口、重新分配行为归属）→ 记录证据和建议，停止相关修改，不静默重写。

修复需要涉及当前任务范围外的文件时，说明情况并停止该修复，不自行扩大范围。
