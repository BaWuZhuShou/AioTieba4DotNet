# 执行与集成计划

## 规划评审门槛

- [x] 三份父任务文档、两份子任务的需求/设计/计划及上下文清单通过静态检查。
- [x] 向用户展示最新目标、首批范围、暂缓项、验收和环境限制。
- [x] 用户在后续消息中批准最新摘要后，才激活子任务 A；父任务不作为实施目标。

## 顺序与完成条件

1. 按子任务 A 计划补齐兼容 SDK、还原并构建现有产品，记录基线来源；新增公开元数据快照及吧信息查询表征。由 Trellis 检查代理复核后主会话创建工作提交，再按工作流归档并记录子任务。
2. 仅在 A 检查通过且提交后激活 B，按其设计迁移内部职责，保持 A 的基线内容不变。由检查代理复核、主会话提交并完成子任务收尾。
3. 复用最终源码的验证结果，父任务核对各子任务结果覆盖 AC1–AC5；若最终集成又修改产品代码，重跑受影响检查。
4. 主会话用 `trellis-update-spec` 维护已落地的内部查询所有权和验证规范，用 `trellis-finish-work` 完成父任务收尾。先工作提交，再归档/日志提交。

## 验证约束

- 还原：`dotnet restore AioTieba4DotNet.sln --locked-mode`。
- 编译：`dotnet build AioTieba4DotNet.sln --configuration Release --no-restore`。
- 离线测试：严格采用子任务中的完整类名白名单；不运行未筛选的 Governance，也不使用 `Contract:Architecture` 作为离线保证。
- 文档/证据检查：`bash scripts/verify-local.sh --validate-only`，四个既有证据缺失时记录不通过及原因；不得自行降低必需性或生成虚假的历史证据。
- 收尾：`git diff --check`、任务 JSONL 校验、暂存范围核对和最终 HEAD 记录。
- 不改 CI build-only 规则，不将本地测试加入 GitHub Actions。

## 集成验收表

| 标准 | 证据来源 |
| --- | --- |
| AC1 | A 的公开基线与 B 最终程序集比较、既有公开结构测试 |
| AC2 | A 的行为表征在 A/B 两阶段的通过记录 |
| AC3 | B 的依赖检查、代码评审、对象图与缓存隔离断言 |
| AC4 | 两个工作提交及归档记录，B 完整回退边界 |
| AC5 | 还原/构建/离线测试结果，以及独立列出的环境和证据缺口 |

## 回退点

产品开始修改前保存 A 的检查结果及提交号。B 检查失败时在其范围内修复；发现不可兼容的真实行为变化则回到规划，不更新基线来获得绿色结果。B 必须能够整体撤销，而 A 的基线仍通过原产品实现。
