# 保持对外兼容的内部架构演进

## 目标与用户价值

在调用方无需修改接入代码的前提下，改善内部职责和依赖关系。本轮完成“兼容性基线 + 吧信息查询解耦”这个可验证的首批交付，并记录后续演进候选。

原始要求：保持对外稳定性，改善内部代码结构和体系，使架构更先进、更易维护。这里的维护性具体指：调用方依赖所需的最小内部能力，同类查询与缓存加载有明确所有者，内部调整能被稳定的契约测试约束。

## 背景与依据

- 2026-09-26 用户先授权创建任务并进入规划，随后回复“批准”，明确批准本文件及设计、计划的最终摘要和两个子任务的实施。
- 规划起点：`b9a86af`，`master` 分支，创建任务前工作区干净。
- 现有定位与约束见 `.trellis/spec/project-positioning.md`：.NET 10 / C# 14，六模块，直接构造 / DI / 工厂三种接入方式，固定 aiotieba 基线。
- `AioTieba4DotNet/Clients/TiebaClientComposition.cs:32` 已统一创建客户端对象图；现有模块、协议、请求、传输、会话、映射分层予以沿用。
- `AioTieba4DotNet/Protocols/ForumProtocol.cs:39` 与 `AioTieba4DotNet/Protocols/AdminProtocol.cs:314` 重复维护吧 ID 查询流程，但认证前置和操作名不同，不能直接互换。
- `AioTieba4DotNet/Protocols/ThreadProtocol.cs:25` 与 `AioTieba4DotNet/Protocols/UserProtocol.cs:33` 依赖整个 `IForumProtocol`；前者实际需要吧 ID、吧名和分类 ID 查询，后者只需吧 ID 查询。
- 现有测试覆盖部分公开结构与行为，缺少完整的公开 API 元数据基线。证据和具体限制见本任务 `research/`。

## 验收标准

- [x] AC1（R1）：全库对外可见 API 元数据与重构前基线无变化；三种入口和六模块保持原样。元数据检查的维度和局限有明确说明，不将其等同于全部运行时兼容性证明。
- [x] AC2（R2）：同一组离线行为表征在重构前后通过，覆盖冷/热缓存、成功/失败/取消、访客/认证前置、名称与 ID 查询、管理操作顺序和跨客户端隔离。
- [x] AC3（R3）：Thread/User 不再依赖完整 `IForumProtocol`；Forum/Admin 的重复 ID 请求加载逻辑收敛；不引入循环依赖、全局状态或新公共类型。
- [x] AC4（R4）：A、B 各有检查结果和本地工作提交（`9b1afc1`、`2491c86`）；B 可整体回退而保留 A 的验证基线；父任务评审核对最终产品提交与检查过的源码一致。
- [x] AC5（R5）：锁定还原、Release 构建及选定离线测试通过后才声称相应通过；无法运行的检查记录原因，证据缺失不算通过。

## 范围外与后续候选

- 不改变公开 API、包身份、目标框架、依赖版本、上游基线或新功能范围；历史 v2→v3 ADR 中允许的破坏性调整不构成本轮授权。
- 不改变 HTTP/WS 重试、回退、状态提交与锁边界，不增加缓存 TTL、淘汰、合并并发请求或释放行为。
- 不修改请求签名算法、线协议、protobuf、生成器或公开映射结果。
- 参数校验复用、ContentMapper 收敛、WS 载荷重复处理、会话状态提交归属及更强的传输基线列为后续独立规划候选。
- 本轮不运行真实在线写入、不发布、不推送远程；离线通过不等于线上已验证或全库完全对齐。
