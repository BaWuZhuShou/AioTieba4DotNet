# 内部架构演进设计

## 决策与边界

保留现有客户端组合根、六模块、协议编排、调度器、传输、请求和映射层。本轮优化内部协作边界，以公开元数据及受影响行为的基线保护调用方。

不增加框架、包或新的公开抽象。没有代码证据支持替换现有 HTTP/WS 架构。查到的生命周期锁与提交分离是后续设计风险，不在未复现和未设计前当作既有缺陷修正。

## 分阶段结构

1. 子任务 A 在未改产品逻辑的源码上建立公开元数据基线和吧信息行为表征，复用现有 Governance 测试宿主、受控传输和会话构造方式。
2. 子任务 B 以小型内部查询协作者承接吧身份解析和缓存加载，并按消费者需要提供窄接口。分类查询仍保持其独立职责；不把它误当作吧 ID 查询。
3. 父任务在两者提交后核对最终 HEAD 的对外差异、离线行为及结构收益。

目标数据流：

```text
公开 Contracts / Modules（保持）
  └─ Forum / Thread / User / Admin 协议
       ├─ 窄吧身份查询能力 → 内部查询协作者 → 原 dispatcher / Api
       └─ 窄分类查询能力 → 既有分类查询实现 → 原 dispatcher / Api
                                 ↓
                    当前客户端独立的 ForumInfoCache
```

所有对象继续由 `TiebaClientComposition` 构造。不得让内部查询协作者反向依赖调用它的 ForumProtocol，也不得新增第二份字典。详细接口和加载边界以子任务 B 的设计为准。

## 必须保留的非显然行为

- Forum 的 ID 查询先检查取消，再查缓存；未命中执行访客可用的 `GetFidAsync` 描述符。
- Admin 的辅助 ID 解析先查缓存；命中时跳过该辅助阶段的认证前置，未命中才执行调用方操作的权限/TBS 前置；查询描述符名仍为 `${operationName}ResolveFid`。实际管理操作自身的认证保持。
- 返回 0、空名称、异常和缓存写入顺序按现状保留，不夹带缓存碰撞、无效输入或新鲜度修复。
- GetFname 的详情请求、详情返回 ID/名称的缓存更新以及按原请求 ID 写入的行为须逐项表征，不只测试正常 ID 相等的情况。
- 失败不能缓存成功结果；取消传播与网络调用次数不能随抽取变化；每客户端缓存互相隔离。

## 兼容性证明与取舍

公开 API 元数据基线检查静态契约，行为表征检查本次改变的运行路径；两者互补。基线不能从重构后的产物倒推，也不能在测试中自动接受更新。对所有公共和受保护可见成员应有稳定排序和明确的快照规则。

不将现有传输测试中的已知差异容许规则解释为严格相等证据。当前阶段的优势是改动范围窄，能先建立确定性的离线结果，不依赖真实贴吧写入。

## 回退与后续路线

- A 是独立验证改进，B 回退时予以保留。
- B 的组合根、内部接口、查询实现和消费者作为一个可逆工作提交，避免留下混合对象图。
- 后续优先按收益/风险分别规划：精确相同的参数校验复用；ContentMapper 的重复聚合和分派；WS 载荷处理；会话状态提交责任。先补对应行为差异基线，再迁移。
- 暂缓项不是本轮隐式实施授权。真实线上验证和发布需要另外明确范围。
