# 思考指南

> **目的**：拓宽思考范围，发现原本可能遗漏的问题。

---

## 为什么需要思考指南？

**多数缺陷与技术债源于“没想到”，而非缺少技能**：

- 没想到层间边界上的情况 → 跨层缺陷。
- 没想到代码模式会重复 → 到处出现重复代码。
- 没想到边界情况 → 运行时错误。
- 没想到后续维护者 → 代码难以阅读。

这些指南帮助你**在编码前提出正确的问题**。

## 速查：触发思考的信号

### 何时思考跨层问题

- [ ] 功能涉及三个或更多层次（本库如契约、模块、协议、传输、映射）。
- [ ] 数据格式在层间发生变化。
- [ ] 多个使用方需要相同数据。
- [ ] 不确定某段逻辑应放在哪里。
- [ ] 正在增加事件种类、JSONL 记录、RPC 载荷或配置字段。
- [ ] 界面／命令代码开始直接对原始载荷字段进行类型断言。

→ 阅读[跨层思考指南](./cross-layer-thinking-guide.md)。

### 何时思考代码复用

- [ ] 正在编写与既有代码相似的代码。
- [ ] 同一模式重复出现三次或更多次。
- [ ] 正在多个位置新增同一字段。
- [ ] **正在修改任何常量或配置。**
- [ ] **正在创建新的工具／辅助函数。** ← 先搜索！
- [ ] 两个文件在本地以类型断言读取同一个无类型载荷字段。
- [ ] 多个分支根据 `kind`／`action` 更新同一派生状态。

→ 阅读[代码复用思考指南](./code-reuse-thinking-guide.md)。

### 核验 AI 交叉审查结果时

- [ ] 审查者声称“用户输入可能恶意” → 核对实际数据源：内部清单、用户配置还是外部 API？
- [ ] 审查者指出“缺少校验” → 数据是否来自受信任的内部来源？
- [ ] 审查者声称“行为改变” → 阅读代码注释，确定是否为有意设计。
- [ ] 审查者在测试中指出“缺陷” → 设想删除被测功能后测试是否仍通过；若是，则测试属于自证式断言。

**AI 审查常见的误报模式**：

1. **信任边界混淆**：将随包内部数据（如 JSON 清单）视为不可信外部输入。
2. **忽视设计注释**：将代码注释明确记录的有意行为标为缺陷。
3. **误读变量**：未追踪到变量真实定义，例如混淆按路径还是按名称作为键的 Map。

**核验规则**：每条 `CRITICAL`／`WARNING` 发现都必须先对照实际代码核验，再排定优先级。既有通用指南按约 35% 的 AI 审查误报预留核验精力；这不是本项目实测统计。

## 修改前规则（关键）

> **修改任何值之前，都必须先搜索！**

```bash
# 搜索即将修改的值
rg -n "value_to_change" .
```

这一习惯可以避免大多数“忘记更新某处”的缺陷。

## 如何使用本目录

1. **编码前**：浏览相关思考指南。
2. **编码时**：感到重复或复杂时，查阅指南。
3. **修复缺陷后**：将新认识补充至对应指南，从错误中学习。
