# 跨层思考指南

> **目的**：实施前梳理跨层数据流。

---

## 问题

**多数缺陷发生在层间边界**，而不是层内。

常见跨层缺陷：

- 上游 API 返回格式 A，而 mapper 期待格式 B。
- 协议层获得字段 X，映射为公开 DTO 的 Y 时丢失数据。
- 多个层以不同方式实现同一逻辑。

---

## 实施跨层功能前

### 第一步：绘制数据流

画出数据如何流动。本库的典型调用与结果路径为：

```text
公开契约 → 模块 → 协议 → 传输／请求 → 响应解析 → mapper → 公开 DTO → 使用者／文档与证据
```

从通用角度，也要考虑数据来源、转换、保存、取回、再次转换与展示；本库有会话和内存缓存，没有数据库层。

对每一个箭头提出问题：

- 数据是什么格式？
- 可能发生什么错误？
- 谁负责校验？

### 第二步：识别边界

| 边界 | 常见问题 |
| --- | --- |
| 公开契约 ↔ 模块／协议 | 类型不匹配、参数或默认值遗漏 |
| 协议 ↔ 传输／请求 | 编码转换、认证前置条件、空值处理 |
| 响应／mapper ↔ 公开 DTO | 序列化语义、日期格式、字段丢失 |
| 公开 DTO／入口 ↔ 文档／使用者 | 签名、属性形态和生命周期说明漂移 |

### 第三步：定义契约

对每个边界明确：

- 精确的输入格式是什么？
- 精确的输出格式是什么？
- 可能出现哪些错误？

## 常见跨层错误

### 错误一：隐式假定格式

**不推荐**：不检查就假定日期格式。

**推荐**：在边界显式转换格式。

### 错误二：校验散落各处

**不推荐**：多个层重复校验同一事项。

**推荐**：明确负责该事项的入口，在那里统一校验；其他边界仍保留各自不同职责的校验。

### 错误三：抽象泄漏

**不推荐**：公开 DTO 需要知道 protobuf 传输结构或端点解码细节。

**推荐**：每层只依赖相邻层的约定，通过稳定契约交互。

### 错误四：每个使用方都解析同一载荷

**不推荐**：命令读取 JSONL 事件，并在本地对字段进行类型断言：

```typescript
const thread = (ev as { thread?: string }).thread;
const labels = (ev as { labels?: string[] }).labels;
```

这是通用／Trellis 事件示例，不表示本库有 TypeScript 业务层。代码看似局部，却意味着每个使用方都维护私有版本的事件契约。下次字段变化可能更新一个命令，却遗漏另一个。

**推荐**：在事件边界解码一次，再导出有类型的投影：

```typescript
if (!isThreadEvent(ev)) return false;
return ev.thread === filter.thread;
```

**规则**：对于只追加日志、JSON 流、RPC 载荷或配置文件，下列内容都应由一个明确所有者负责：

- 事件／载荷类型定义。
- 类型守卫及从 `unknown` 开始的归一化。
- 界面命令使用的元数据投影。
- 从权威来源重放状态的归约器。

渲染代码可以格式化字段，但不能重新定义载荷契约。

- [ ] 已定义每个边界的格式。
- [ ] 已确定校验位置。

实施后：

- [ ] 已验证每个边界的错误处理。

## 跨平台模板一致性

在 Trellis 上游，不同平台上的命令模板（如 `record-session.md`）内容相同或近似相同。这也是跨层边界。本节中的 `src/templates/` 路径属于上游，不表示本项目存在该目录。

### 检查清单：修改任一命令模板后

- [ ] 找到所有平台的同名命令：`rg --files src/templates -g '<command>.*'`，再核对其是否位于各平台的 `commands/trellis/` 目录。
- [ ] 更新所有平台副本，包括 Markdown `.md` 和 TOML `.toml`。
- [ ] 对 Gemini TOML，适配续行反斜杠（`\\` 与 `\`）及三引号字符串。
- [ ] 在提供该命令的上游环境中运行 `/trellis:check-cross-layer`，验证无遗漏；本项目使用可用的 `trellis-check` 技能完成对应检查。

**实际案例**：Claude 的 `record-session.md` 改用 `--mode record`，却遗漏了 iFlow、Kilo、OpenCode 和 Gemini；跨层检查发现了问题。

---

## 生成运行时模板的升级一致性

一些生成文件同时是文档和运行时输入。在 Trellis 中，`.trellis/workflow.md` 会被 `get_context.py`、`workflow_phase.py`、SessionStart 过滤器和逐轮 hook 解析。模板变化必须同时验证全新初始化与升级路径。

### 检查清单：修改运行时解析的模板后

- [ ] 找到所有读取模板的运行时解析器，不仅是安装文件的写入器。
- [ ] 检查相关语法是否位于标签块等显式管理区域之外。
- [ ] 在维护上游模板时，验证全新 `init` 输出，以及写入较旧 `.trellis/.version` 的版本化 `update` 场景。
- [ ] 使用旧版未修改模板夹具增加升级回归，断言安装文件达到当前随包模板的形态。
- [ ] 更新负责该运行时契约的规范；本项目的中文定制边界见 [Trellis 中文维护与自动提交](../trellis-localization.md)。

这些初始化／升级检查应在隔离夹具或上游测试环境中完成，不要求为本次本地规范维护运行真实 `trellis update`。

---

## 版本化文档边界

版本化文档也是跨层边界：源码路径、`docs.json` 版本路由和渲染后的版本选择器必须描述同一发布线。以下是 Trellis 上游文档站示例；本项目当前使用 VitePress，不能据此假定存在 MDX、`docs.json` 或这些目录。

### 检查清单：编辑版本化文档前

- [ ] 确定目标发布线：stable、beta 或 RC。
- [ ] 核验编辑的 MDX 路径与发布线匹配：stable 为 `docs-site/{start,advanced,...}` 及 `docs-site/zh/{start,advanced,...}`；beta 为 `docs-site/beta/**` 及 `docs-site/zh/beta/**`；RC 为 `docs-site/rc/**` 及 `docs-site/zh/rc/**`。
- [ ] 核验 `docs.json` 导航将版本标签指向同一组路径。
- [ ] 提交前用 `rg` 搜索另一棵目录树中的发布线专用术语。
- [ ] 根发布路径出现 beta 内容时，应视为源码路径错误，而非渲染错误。

**实际案例**：仅属于 beta 的任务工作流变化，将 `prd.md` + `design.md` + `implement.md`、任务创建同意和 Codex 模式提示写入根 `start/`、`advanced/` 路径，导致文档站在 `Release` 选择项下展示 0.6 beta 行为。修复方法是恢复根发布文档，将 0.6 内容移至 `beta/`、`zh/beta/`，并增加对根发布树中 beta 标记的搜索审计。

**实际案例**：Codex inline 模式将工作流平台标记从 `[Codex]`／`[Kilo, Antigravity, Windsurf]` 改为 `[codex-sub-agent]`／`[codex-inline, Kilo, Antigravity, Windsurf]`。全新初始化正常，但 `trellis update` 只合并 `[workflow-state:*]` 块，保留了块外旧标记。升级后的项目因此获得新 hook 脚本却仍使用旧工作流路由，`get_context.py --mode phase --platform codex` 可能返回空的阶段 2.1 细节。

## 模式探测检查清单

CLI 通过探测远程资源自动判断模式时，例如检查 `index.json` 是否存在以选择市场模式还是直接下载模式，应遵循以下检查。

### 实施前

- [ ] 探测覆盖所有依赖结果的代码路径，包括交互、`-y` 和 `--flag` 组合。
- [ ] 区分 404 与临时错误，不能都视为“未找到”。
- [ ] 临时错误必须中止或重试，不能静默切换模式。
- [ ] 上下文变化时重置共享状态，如缓存、预取数据；例如用户切换来源时。
- [ ] 快捷路径（如 `--template` 跳过选择器）必须具有与探测路径相同的错误处理质量；检查下游函数是否调用一概捕获的包装函数。

### 实施后

- [ ] 从探测结果追踪至每个模式决策分支，不能意外落入其他分支。
- [ ] 外部格式契约（giget URI、原始 URL）有测试，或至少有注释说明。
- [ ] 元数据读取消费完整响应，或使用流式解析器，不能把固定长度前缀当作完整 JSON。
- [ ] 从解析部件重建复合标识时，确认所有字段都包含在正确位置，例如 `provider:repo/path#ref`，而非 `provider:repo#ref/path`。
- [ ] 快捷路径后调用的操作函数不能内部沿用旧的一概捕获获取逻辑；需要区分错误时，必须使用与探测相同质量的实现。

**实际案例**：Trellis 上游自定义注册表流程经历三轮审查，共发现八个缺陷，包括：探测只在交互模式运行；临时错误落入错误模式；giget URI 的 `#ref` 位置错误；预取模板在切换来源后泄漏；`--template` 快捷路径绕过探测，而 `downloadTemplateById` 内部使用一概捕获的 `fetchTemplateIndex`，将超时误报为原始诊断 `Template not found`（未找到模板）。

**实际案例**：代理会话更新提示曾使用 `response.read(4096)` 获取 npm `latest` 元数据，然后按完整 JSON 解析。`@mindfoldhq/trellis` 包元数据超过 4 KB，导致 JSON 截断、解析静默失败，首次会话注入也没有更新提示。修复方法是先读取完整响应再解析，并增加 `version` 后跟 8 KB 元数据尾部的回归。

## 何时编写流程文档

以下情况应编写详细流程文档：

- 功能横跨三个或更多层次。
- 涉及多个团队。
- 数据格式复杂。
- 该功能以前引发过缺陷。

---

## 事件日志／投影边界

只追加日志属于跨层契约。单个事件经过以下路径：

```text
CLI 输入 → 事件写入器 → events.jsonl → 读取器 → 过滤器 → 归约器 → 展示
```

### 检查清单：新增事件种类或字段后

- [ ] 将事件种类加入中央事件分类定义。
- [ ] 在事件层添加带类型的事件变体或类型守卫。
- [ ] 为来自用户输入或 JSON 的数组／对象字段添加归一化辅助逻辑。
- [ ] `seq`／`id` 的分配只保留在事件写入器中。
- [ ] 让过滤器和归约器使用带类型的事件守卫，而非本地类型断言。
- [ ] 让展示代码使用归约器输出或带类型事件，而非原始 JSON。
- [ ] 至少增加一个回归，证明历史重放和实时过滤使用同一个过滤模型。

**实际案例**：Trellis 线程频道增加了 `kind: "thread"`、`description`、`context`、标签和 `lastSeq`。首次实现能正确重放线程状态，但多个命令仍通过本地类型断言重新解析事件载荷字段。修复方法是让核心事件层拥有 `ThreadChannelEvent` 和 `isThreadEvent`，让 `reduceChannelMetadata` 成为唯一的频道元数据投影，并让 `reduceThreads` 成为唯一的线程重放归约器。
